# Discord release announcements

This is separate from the nightly changelog. The release observer has no
webhook and does not check out the tag. The sender executes reviewed code
from the default develop branch and uses the existing discord-changelog
environment; keep its develop-only policy and dedicated Discord webhook.

Only published stable or preview releases are candidates. The sender
confirms the event tag and commit, refetches the public GitHub release,
and checks the active signed live catalog with the launcher's public
trust configuration. A release is not ready if any affected target is
unavailable. A lagging feed is checked five times at 30-second intervals;
no message or reservation is created if the feed never matches. A later
catalog renewal alone does not raise a release event.

## Labeling releases

A simple launcher-only or runtime-only release can identify its target in
the first paragraph (for example, “This update improves the launcher”),
with the same version in its tag and signed promoted entry. For bundled
releases with independently versioned targets, specify exact versions
at the end of the published notes, for example:

```text
<!-- corecritical-discord-targets: corecritical=1.0.58,mw3=1.0.48 -->
```

Use only the affected product keys: corecritical for the launcher, mw3
for its MW3-RE runtime. A historical release with no way to bind its
independent targets is intentionally ineligible, even in dry run. Use a
first paragraph with short public, player-facing changes and no private
download references. The bot adds only the canonical GitHub release link.

## Verify and activate

Run **Announce CoreCritical release** on develop with a public numeric
release ID. Manual runs are dry only and cannot create reservations,
access the Discord environment, or send. Confirm the source publisher's
normal method triggers the release observer; a release published with
GitHub Actions' built-in GITHUB_TOKEN does not trigger this workflow.
Confirm the observer is present in the next release tag's commit.
If promotion to main is needed, use the normal promotion PR.
For the first live run, use a future legitimate release, not a test tag.

After review and authorization, set the repository Actions variable
DISCORD_RELEASE_ACTIVATION to JSON containing the current UTC timestamp
and both exact currently promoted product versions, obtained from the
verified signed catalog. For example (use current values, not these):

```json
{"since":"2026-11-26T16:00:00Z","corecritical":"1.0.58","mw3":"1.0.48"}
```

Without this variable announcements are off. Candidates must be published
after activation, be no older than 24 hours, and advance at least one
affected product from the baseline. Check the job summary for a verified
Discord message link. A date slot in the daily changelog is never used.

## Recovery

A release reservation artifact is written before Discord delivery.
Never delete it or resend if delivery is uncertain; check the channel
and job first. Manual Actions reruns cannot post. If the release event
did not arrive or the feed missed the retry window, no message is sent.
Remove DISCORD_RELEASE_ACTIVATION or disable the new sender to stop
announcements without affecting the daily changelog. No historical posts
are generated by activation, and stopping does not remove prior posts.
