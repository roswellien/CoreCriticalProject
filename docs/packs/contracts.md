# Content pack contracts

Five agreements that the runtime, the launcher, the mod tools and pack authors are all
built against. A part of the system may assume only what a contract says about another
part, never how that part happens to be written.

All five are at **version 0 (draft)**. Each section separates what exists today from what
is proposed, and ends with the questions still open. Closing those questions, and adding a
schema file and example packs for each contract, is the first work of
[workstream A](workstreams.md#a-contracts-and-example-packs). How a contract changes is in
[Changing a contract](workstreams.md#changing-a-contract).

Background and the decisions these follow from: [README](README.md).

## 1. Pack manifest

### Today

`pack.json` at the root of a `.mw3pack` archive
(`tools/mw3-remaster-launcher/Core/PackManifest.cs`). Schema versions 1 and 2 are in use.

- Identity: `schema_version`, `game_id`, `id`, `name`, `version`, `author`, `homepage`,
  `description`, `category`.
- Compatibility: `min_engine_version`, `dependencies` (each `id`, `min_version`,
  `optional`), `conflicts`.
- `provides`: `mechs`, `world_models`, `textures`, `normal_maps`, `audio`, `cd_music`.
- `native_payload`: `profile`, `registry`, `path_base`, `required_formats`,
  `required_capabilities`. The registry is a second JSON file whose shape depends on the
  profile.
- `files`: every file's `sha256`, `bytes` and optional `format`.

### Proposed for schema version 3

Additions only. A schema 1 or 2 pack keeps working unchanged.

- **`gameplay`**: an object with `root`, the folder inside the pack that holds an ordinary
  mod (a `mod.txt` and files laid out like the game's install). Everything
  [modding.md](../../runtime/mw3-re/docs/modding.md) allows in a mod is allowed here and
  nothing else. The pack's `id` is the mod's folder name once installed.
- **`visuals`**: a list of bindings, one per thing dressed. Each names a `target` (see
  [contract 4](#4-visual-binding-rules)), a `kind` (`model`, `skin`, `environment`,
  `ui`, `music`, `cinematic`) and the pack-relative files for it. This replaces reading a
  differently shaped registry per profile.
- **`provides`** becomes a plain summary for display, generated by the pack tool from the
  two sections above: counts and names of mechs, weapons, skins, maps, missions and
  campaigns. Nothing may decide behaviour from it.
- A pack with a `gameplay` section counts toward the multiplayer match check. A pack with
  only `visuals` never does.

### Rules

- Data only. An archive holding an executable, a script or a library is refused at
  install.
- Every file in the archive is in `files`, and every entry in `files` is in the archive.
- Paths are relative, use `/`, and never contain `..`, a drive or a leading slash.
- An unknown field is an error in schema 3. A pack author finds a typing mistake at build
  time, not in the game.

### Open questions

- Whether `mod.txt` stays the authored file for gameplay rows, or the pack tool generates
  it from JSON in `pack.json`. Proposed: `mod.txt` stays, since the runtime, its
  reference and its editor already read and write it.
- How a pack declares that its visuals need its own gameplay payload turned on.

## 2. Installed layout

### Today

- The launcher's pack library is `<pack base>/mods/<pack id>/` with the manifest at its
  root (`PackManager.cs`, `PackStorage.cs`). Install extracts to a staging folder, checks
  every hash, then moves it into place.
- The runtime's mods are `<write dir>\mods\<name>\`
  (`runtime/mw3-re/src/mech3/mods.cpp`). The player's own imports live there.
- Ticks are `<write dir>\campaigns\<entry>\mods.txt`, one `mod=<name>` line each, first
  line wins a shared file. Entries are `mw3` (the game's campaign), `ia` (Instant
  Action), `mp` (multiplayer), `<mod>~<id>` for a mod's campaign, and the player's copies
  (`runtime/mw3-re/src/upgrades/mods/campaign_entries.cpp`).
- The runtime marks folders it made with a marker file and deletes only folders that
  carry one.

### Proposed

- **A second, read-only mods folder.** The launcher installs a pack whole into its own
  library, as today. The runtime is told that library's location and treats each pack's
  `gameplay.root` as one more mod, after the player's own `mods\` in the search order.
  The launcher never writes into `<write dir>\mods\`, so it can never damage a mod the
  player imported, and uninstalling a pack is deleting one folder.
- **A name clash is refused, not resolved.** A pack whose `id` matches a folder in the
  player's `mods\` is listed with a plain message and left off.
- **Ticks stay in the runtime's files.** The launcher turns a pack on or off for an entry
  by editing that entry's `mods.txt` with the same write-beside-and-rename the runtime
  uses. It holds no second copy of that state.
- **Default ticks at install.** The launcher adds the pack to `ia` and `mp`, and to each
  custom campaign entry present. It never adds it to `mw3`. A pack whose own campaign
  needs it is ticked and locked for that campaign by the runtime, as today.
- **Uninstall** removes the pack folder and its lines from every `mods.txt`. Saves are
  left alone; the runtime already names a missing mech or weapon.

### Open questions

- Whether the runtime may run while the launcher edits a tick file. Proposed: the
  launcher edits only while no game process is running, and says so.
- Whether multiplayer should take new packs by default or only on a first prompt, since
  it changes who a player can join.

## 3. Runtime content report

### Today

The runtime prints lists for people: `mw3 --mods` lists mods and which are on,
`--mod-report` and `--check-mod` describe one mod. The launcher works out what a visual
pack provides by reading the pack's registry itself, a second implementation of what the
runtime will do.

### Proposed

One command prints one JSON document and exits: `mw3 --content-report`, with the same
install, write directory and pack library arguments a normal start takes. It mounts
nothing and starts no game.

The document lists, for each pack and each player mod found:

- its identity, version and where it was found;
- what it adds, by kind, each item with a stable name and a display name: mechs, weapons,
  skins, Instant Action maps, missions, campaigns, and each visual binding with its
  target;
- which entries it is ticked for;
- every problem, each with a short code, a plain sentence, and the file and line where
  that applies. A problem is either an error (the item or pack is left out) or a warning
  (it is used).

The launcher and Mod Studio show this report. Neither works out for itself what a pack
contains or whether it is valid, so the three can never disagree.

### Rules

- A broken pack never stops the game. It is left out and named.
- The report for a given set of files is the same on every run, in the same order.
- The document carries its own `report_version`. A reader refuses a major version it does
  not know.

### Open questions

- Whether a failed mesh or texture decode is found by this command or only at mission
  load. Proposed: this command checks headers, sizes and names; full decode stays lazy.

## 4. Visual binding rules

### Today

The evidence is in the README, under
[Can an HD model attach to a mech a mod added?](README.md#can-an-hd-model-attach-to-a-mech-a-mod-added)

- An HD model binds to the original model file's name, `mech_<model>.flt`.
- Pack skins bind by the mech's name in the Mech Lab and by the model's name in the
  renderer.
- Environment packs bind by mission and map name.

### Proposed

- **Every visual names a `target`: `<kind>:<name>`.** For a mech model and for skins the
  kind is `mech-model` and the name is the model's, the one a `mech=` line gives as
  `model=`. Two mechs sharing a base model share its HD model and its skins.
- **Skins are keyed by model name everywhere.** The Mech Lab's list and the renderer use
  the same key (gap 2), and the eight-original-skins condition is removed.
- **A mech that wants its own look has its own base model.** A variant that only changes
  numbers borrows a stock model and is drawn as that stock mech.
- **The HD model follows the base model's skeleton.** Each part name the HD model refers
  to exists exactly once in the base model. The pack tool checks this at build time; the
  runtime checks again and falls back to the base model with a named warning.
- **No behaviour is keyed on a chassis name in code.** A fit or correction that one model
  needs (the Orion's guard fit today) is a field in that model's binding.
- **For maps and missions** the kinds are `world:<folder>` and `mission:<world>/<n>`, the
  names a `world=` line and a campaign's `mission=` line already use.

### Open questions

- Where headlight sockets and weapon attachment points for a new base model are declared.
- Whether a pack may add skins to another pack's mech. Proposed: yes, by declaring a
  dependency on it.

## 5. Feed format

### Today

A signed catalogue document: `schema_version`, `type`, `channel`, `sequence`, issue and
expiry times, and a list of packs. Each pack has `id`, `game_id`, `version`, a minimum
runtime version, the archive with its hash, and the manifest hashes of installed copies
it may replace (`tools/mw3-remaster-launcher/Core/AssetPackUpdateCatalog.cs`). There is
one feed, ours.

### Proposed

- **The same document for every feed.** A third party publishes a catalogue in this
  format at an address of their own, and a player adds that address in the launcher.
- **Each feed has its own signing key**, shown to the player as a short fingerprint when
  the feed is added and pinned from then on. A catalogue signed by a different key is
  refused, not offered as an update.
- **A feed can only update packs it first installed.** A third-party feed can never
  replace a pack from our feed or from another feed, whatever `id` it claims.
- **Third-party packs are labelled** with their feed's name wherever they are listed.
- **The safety of a pack never depends on its feed.** Every pack from every feed passes
  the same manifest rules, hash checks and data-only rule at install.

### Open questions

- Whether a pack file dropped in by hand, with no feed, is allowed. Proposed: yes,
  labelled as having no update source.
- Whether we keep a list of known third-party feeds on the website. Not needed for the
  first milestone.
