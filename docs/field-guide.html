MechWarrior 3 recompilation

MW3Recomp Field Guide

How the MW3 recompile works, for anyone curious and for developers who want to help but have never worked on a recompile. Part 1 is the big picture. Part 2 is for contributors.

Part 1 · The starting point

What's inside Mech3.exe

MechWarrior 3 was written in C++ in the late 1990s. A compiler turned that source into machine code, the raw instructions a CPU reads, and only the machine code shipped in Mech3.exe. The original source was never released.

Source code
void Mech::Fire(Weapon& w) {
heat += w.heat;
}

Notice what didn't make it across: the names. Mech, Fire, heat and the structure around them were thrown away. The exe holds only numbers like 8B 46 14 ("load the value 20 bytes into this object"), millions of them.

Part 1 · The options

Three ways to revive an old game

The original exe targets 1999 Windows and DirectX 6-era graphics. On a modern PC it runs poorly or not at all. Preservation projects usually take one of three routes.

The main work is the recompile. A wrapper is kept alongside it as a separate way to play. There is no interpreter anywhere: code that hasn't been translated stops with an address and a reason instead of being run some other way.

Part 1 · How the translation works

Lifting: compiling in reverse

A tool called a lifter runs the trip backwards. It reads the machine code one function at a time and writes out code that does exactly the same thing, which a modern compiler then builds into a native 64-bit program. This project uses Remill, an open-source lifter.

Mech3.exe
56
8B 46 14 01 47 30
5E C3
LifterRemill
Lifted code
void sub_0045A1C0(State& s, Memory& m) {
push(s, s.esi);
s.eax = m.load32(s.esi + 0x14); m.add32(s.edi + 0x30, s.eax);
s.esi = pop(s); return;
}

Illustration, simplified from what a lifter really emits.

The result is correct, but nameless. The function is named after its address in the old exe, and the variables are CPU registers. Proving that sub_0045A1C0 is really "fire weapon" takes evidence, so the project's rule is: unproven functions keep their sub_XXXXXXXX names. A plausible guess would be invented, not readable.

Part 1 · What changes and what doesn't

Original logic, modern services, nothing of the game shared

The translated game still decides everything a mech does. What changes is everything it talks to. And because the translation is made from the copyrighted game, it never leaves the player's machine.

Kept original
  • Gameplay, physics, AI and timing logic
  • Missions and campaign flow
  • The original HUD and menus
Modernized
  • Vulkan rendering, widescreen, anti-aliasing
  • Input, audio, files, Windows integration
  • Optional visual upgrades, kept as separate settings
Never distributed
  • The game, its exe and data
  • The lifted game code
  • Builds made from it

So every player brings their own legally obtained copy of MW3, and everything in the public repository is project-written code around the game.

That's the big picture. Part 2 is for developers who want to help: how the pieces fit, where things live, and the rules that keep the project honest.

Part 2 · Two worlds in one program

Guest and host

The translated game still behaves like a 32-bit program, with 32-bit addresses. The program around it is 64-bit. The project calls the game's world the guest and the new program the host. Most design rules come down to keeping these two apart.

Host · new 64-bit program
Renderer · audio · input · files · Windows integration
Guest · translated game
Expects 1999 Windows. 32-bit addresses into memory the host owns.
Every guest memory access goes through a checked call, never a raw pointer.

A guest address is just a 32-bit number. The guest asks the host for bytes at that address, and the host checks the range before touching anything. From runtime/memory:

// Explicit little-endian serialization permits unaligned x86 accesses on any host.
template <GuestScalar T> [[nodiscard]] T load(GuestAddress address) const {
    std::array<std::byte, sizeof(T)> bytes{};
    read(address, bytes);    // throws MemoryFault outside a mapping
    ...
}

That's why you'll never see a guest value cast to a host pointer, or a host pointer stored in guest memory. Bad accesses become clear errors instead of random crashes.

Part 2 · Replacing 1999 Windows

The game asks for old services, the host answers

The game still calls DirectDraw, Direct3D, Win32, Microsoft's MFC framework and CD audio. In the recompile, each call lands on a project-written host implementation that does the same job with modern parts.

Direct3DDrawPrimitive(triangles)
DirectDrawFlip()

Host bridgeproject-written
What actually runs
VulkanvkCmdDraw
VulkanvkQueuePresentKHR

Simplified. Real bridges handle many calls and state.

Bridges implement the behaviour the game was observed to need, not the whole old API. An unknown call fails loudly; it never returns a fake success. This is also where optional enhancements such as lighting, anti-aliasing and replacement models plug in, separate from gameplay logic.

Part 2 · Finding your way

A map of the repository

Most of the time spent on a first change goes into finding where it belongs. Here is the layout at the folder level.

runtime/Shared host services: checked guest memory, graphics, audio, input, Windows and MFC pieces.
recomp/Where translation output goes. Only README files are committed; generated code stays local.
tools/Exe validation and analysis, the lifting toolchain, launchers, the enhanced renderer, and a lot of dated research.
games/mw3/Version-specific data, symbols and evidence, plus the Mod Tools.
tests/Project-written fixtures and contract tests. No game files.
docs/Architecture, plans, milestones, setup guides and the code guide.

One surprise: some active components live in folders named after the research step that produced them, including the main native host, which sits under tools/ rather than runtime/.

Start heredocs/code-guide.md lists every active component with its current entry files and what to watch for when changing it.
Part 2 · The other workstreams

Launcher, wrapper and Mod Tools

Besides the native host, three other pieces make up the project. Each one is its own area to contribute to.

Launcher players

A Windows app checks the installation and settings, hands off to Python that prepares local files, then starts the host. Planning, preparing and launching are separate steps on purpose.

D7VK wrapper players

Runs the original, unchanged exe with a Vulkan graphics wrapper in an isolated profile. A separate way to play, not a fallback inside the native host.

Mod Tools modders

A desktop map and mission editor and a browser 3D Map Studio. They read the game's own archives, keep the install read-only and export to a separate folder.

Part 2 · Reading the map

Live code versus frozen research

The project keeps its experiments. Much of tools/ is dated research: source models, comparers and acceptance runs whose file hashes are pinned in the project's evidence records. Change one byte and the record no longer matches.

Maintained change freely
  • Components listed in docs/code-guide.md
  • Shared services under runtime/
  • Launchers, editors, tests
Frozen evidence leave as is
  • Dated research folders such as tools/m4-* and tools/x87-*
  • Historical source models and hashes
  • Pinned tools used to measure a result

So even ugly frozen code isn't reformatted, renamed or deleted as cleanup. If something in it is worth reusing, extract it into a reviewed, maintained module and leave the original untouched.

Part 2 · How the project knows things

Evidence first, for progress and for your changes

Progress is tracked as milestones, from the bootstrap through native startup, a playable Training mission and full campaign compatibility to later modernization and other platforms. A milestone only counts with recorded evidence against the original game. A run that works on someone's machine is noted, but it isn't acceptance.

Any checkout no game needed
cmake --preset default
cmake --build --preset default
ctest --preset default

Builds the asset-free runtime and runs the tests, the same as CI. Add -A x64 on Windows with Visual Studio. A format-check target checks C++ formatting.

The full game local setup
  • Your own MW3 installation
  • A prepared local environment and generated lifts
  • Needed for behaviour changes to timing, rendering or input, which need an original-game baseline

Whatever you change, say which checks you ran and which ones need private inputs you couldn't run.

Current statusdocs/project-milestones.md and docs/roadmap.md are kept up to date. This guide deliberately doesn't repeat their numbers.
Part 2 · Your first change

Ground rules

Good first contributions: reproducible bug reports, focused contract tests, readable host-service code, documentation, hardware test reports and editor improvements. CONTRIBUTING.md has the full rules; these are the ones that catch newcomers.

Do
  • Start from an observation and its evidence
  • Work on components the code guide lists as active
  • Keep each change to one behaviour or one readability concern
  • Comment the why: binary layouts, units, ownership, calling conventions
  • Say which checks you ran
Don't
  • Rename sub_XXXXXXXX functions without evidence
  • Reformat or rename frozen research files
  • Mix a formatting pass with gameplay or renderer changes
  • Commit or attach game files, memory dumps, saves or generated translations
  • Make an unknown API return a fake success
