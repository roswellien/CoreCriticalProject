# Globals

How the game builds its global objects at startup. Visual C++ 6 builds every
global C++ object with a constructor before `WinMain` runs: startup
([`WinMainCRTStartup`](startup.md#sub_005ac3a0)) runs the C++ initializer table
at `005E0000` to `005E0244` through [`_initterm`](startup.md#sub_005ac598),
which calls each non-null entry in turn. This file covers the first 15
entries, `005E0004` to `005E003C` (the first word is null). Each points at a
small function the heap-carry
[README](../../../../tools/m4-crt-heap-carry/README.md) calls a "root",
numbered 1 to 15 in table order, and every root has the same shape, laid out
in 80 bytes:

1. The root itself (address A) calls A + `0x10` and then jumps to A + `0x20`.
2. A + `0x10`, the function this file names, loads the object's address into
   ECX and jumps to the object's constructor.
3. A + `0x20` passes the address A + `0x30` to [`atexit`](startup.md#sub_005ac140),
   removes it and returns, so A + `0x30` runs when the program exits.
4. A + `0x30` tests one bit of a flag byte; if the bit is already set, it
   returns. Otherwise it sets the bit, loads the object's address into ECX and
   jumps to the object's destructor. The bit makes sure the destructor runs at
   most once.

This is the code Visual C++ 6 generates for each global object; the functions
are the game's own (the objects belong to the game), even though no one wrote
them by hand.

The constructors fall into four groups, which the names follow: `004C7B80`
builds the library `list` of numbered objects (see [`objects.md`](objects.md));
`004D8540` builds six objects the heap-carry README calls containers (vtable
`005CD0D4`, each with a 12-byte head node), named `List1` to `List6` here; the
six constructors of roots 8 to 13 each call
[`SimpleObject_Init`](objects.md#sub_004c8600) first, named `Simple1` to
`Simple6`; and `004C0310` and `004C0570` build two numbered objects through
[`LinkedNumberedObject_Init`](objects.md#sub_004bf910). Numbers follow the
table's order. The heap-carry README's sections "Main initializer table" and
"Roots 2..7" to "Roots 14..15" describe the same roots, objects and
constructors.

## sub_0040FFF0

**Name and confidence:** `GlobalSetup_ObjectList`, confirmed.

**Kind:** the game's own code, generated by the compiler for one global object.

**Extent:** `0040FFF0` to `0040FFF9`, 10 bytes.

**Callers:** one, root 1 at `0040FFE0`, which calls it from its first
instruction; the root is reached from the initializer table entry at
`005E0004`.

**What it does:** loads the address `00603FD8` into ECX and jumps to the
constructor `004C7B80`, which builds the object and returns straight to the
root. There are no branches and no arguments. The object is
the list of numbered objects described in [`objects.md`](objects.md).

**Reads and writes:** nothing itself; the constructor writes the object.

**How the host reaches it:** `composition.cpp` routes calls to it to the heap
stage, whose table of initializer roots lists root `0040FFE0` with object
`00603FD8` and constructor `004C7B80` and runs its lifted copy of this function
when the root calls it. Context only, not proof.

**Why this name:** the game-code rule. Both instructions are described above,
and its one caller is the initializer root that builds this object.

**Still unknown:** nothing about the name.
